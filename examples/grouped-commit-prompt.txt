根据提供的暂存区 diff，使用简体中文生成一条准确、精炼、按独立变更目的分组的 Git 提交信息。内容只依据可见变更；若输入是摘要或节选，不推测缺失部分。

先在内部提炼行为变化，再合并关联事项、去重，最后组织输出。不要输出分析过程。

分组：
- 每组代表一个可独立说明的用户能力、问题修复或维护目的，不按文件、配置键、实现步骤或接入位置拆组。
- 服务于同一目的的配置、命令行与钩子接入、测试、文档和示例，优先并入同一组；只有存在独立使用场景或独立问题时才另起一组。
- 合并组后若能用具体标题准确概括，且条目仍围绕同一目的，就保留合并；若只能用“优化多个功能”等空泛标题概括，则拆开。不要仅因同属一个模块而合并无关变更。
- 例如，为同一生成流程新增格式选择、默认提示词保存和正文开关时，可以合为一组，分别说明新增行为；独立的配置解析错误另列修复组。仅示范判断方法，不套用内容或组数。
- 覆盖重要行为变化和独立修复；不要求每个改动点都成为一个标题或条目。组数随实际内容决定，只有一个目的时只写一组。

标题与正文：
- 每组使用 <type>(<scope>): 描述，标题说明这一组最终改变了什么，避免“完善功能”“优化体验”等空泛措辞。scope 沿用真实模块命名，没有明确模块时省略。
- 每组独立选择 feat、fix、docs、refactor、perf、test、build、ci、chore、style 或 revert；新能力用 feat，行为纠错用 fix，style 仅用于代码格式变化。不编造破坏性变更。
- 标题描述只写本组结论；正文用“- ”列出标题未交代的关键行为、适用范围、优先级、边界条件或兼容规则。
- 同一事实在全文只表达一次；标题概括后，条目必须增加具体信息，不能换词复述标题。同一选项在命令行、钩子等入口的相同行为合成一条。
- 一条只表达一个有意义的变化，密切相关的规则可合写；只保留有助于理解本次提交的细节。不要凑条目，也不强制每组相同条目数。
- 随附文档、示例、测试通常省略；只有涉及重要用法、兼容性或独立工作时才写。不要逐文件罗列或把代码实现步骤写成流水账。
- 使用直接、具体的动作表达。不要添加无信息量的“支持”“可通过”等套话；保留能说明新能力或条件限制的必要措辞。
- 不编造动机、收益、issue 编号或测试结果，不将文档中的历史功能当作本次新增实现。

输出结构（占位内容仅示范排版，不要求固定组数或条目数）：
<type>(<scope>): 第一个独立目的

- 标题之外的关键行为
- 必要的边界或优先级规则

<type>(<scope>): 另一个独立目的

- 对应的具体变化

每组标题后、组与组之间空一行。整体是一条提交信息，不添加覆盖全部分组的全局总标题。标题不超过 72 个字符，意思完整，不用省略号截断。

输出前在内部检查：能否合并目的相同的组？是否有标题与条目、条目与条目重复？删掉某条是否会丢失重要行为信息？据此合并或删减，并确认独立变更未遗漏。

只输出可直接存入 Git 的纯文本，不加粗，不使用代码围栏、Markdown 标题、编号或分隔线，不添加解释、结语或外层引号。
